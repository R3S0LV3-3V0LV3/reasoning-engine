======================================================================

Implement Wave 3 of the Frontier Reasoning Engine as the semantic front end that converts a canonical TaskEnvelope into a typed TaskSignature, an enforceable BudgetPlan through the already-frozen M02, a provenance-rich ProblemSpec, and one or more deterministic representation projections.

Wave 3 must add:

- a deterministic, versioned prompt registry;
- a deterministic, versioned structured-output schema registry;
- provider-neutral StructuredModelPort result semantics suitable for semantic modules;
- an artifact-backed SemanticModelRuntime for idempotent semantic calls;
- strict raw-output / parsed-proposal / canonical-state separation;
- one metered structured-output repair attempt where policy permits;
- deterministic conservative fallbacks;
- shared SourceAnchor semantics;
- shared epistemic extraction labels;
- M01 — Task Classifier;
- M03 — Problem Formaliser;
- M04 — Representation Selector;
- deterministic representation builders and projection hashes;
- Wave 3 event vocabulary, reducer/state extensions, snapshots, replay and differential-replay coverage;
- integration of newly available semantic state with the frozen M09, M02, Budget Meter, M12, and M13 substrate;
- complete unit, property, integration, golden, backward-compatibility, and replay tests.

Wave 3 is the first model-assisted semantic wave.

Its defining architectural problem is therefore:

Introduce nondeterministic semantic assistance without allowing nondeterministic model behavior, prompt drift, malformed structured output, unsupported inference, provider-specific behavior, or low-confidence guesses to mutate canonical state implicitly.

The Wave 3 output is not an agent loop and not a candidate-search engine.

Wave 3 must guarantee:

- prompt/version provenance;
- model-output provenance;
- strict schema and semantic validation;
- provider neutrality;
- replay without model re-execution;
- monotone task classification;
- harder-is-higher difficulty axes;
- irreversibility rather than reversibility in allocation-facing state;
- deterministic risk floors that model output cannot lower;
- explicit epistemic labeling;
- source-anchored explicit input;
- no inference-to-fact collapse;
- no hidden assumptions;
- hard-constraint non-demotion;
- HARD + UNKNOWN preservation;
- contradiction surfacing;
- deterministic representation selection;
- complementary views under a versioned tie-band policy;
- deterministic representation projection hashes;
- preservation of all accepted Waves 0–2 invariants.

5. BINDING WAVE 3 ARCHITECTURAL DECISIONS
======================================================================

5.1 Model output is an untrusted semantic proposal

A model response is never canonical state merely because it parsed successfully.

The required path is:

transport result
→ strict output-schema validation
→ deterministic module semantic validation
→ invariant validation
→ typed event validation
→ atomic commit
→ deterministic reduction

Raw response, parsed proposal, and accepted canonical state are distinct objects/concepts.

5.2 Prompts are versioned executable configuration

Prompts must not exist as anonymous, duplicated module-local strings.

Every semantic prompt has:

- stable prompt ID;
- explicit prompt version;
- deterministic template hash;
- input contract version;
- output schema ID/version;
- model role;
- module/operation identity.

Changing a material prompt under the same prompt version is a configuration integrity defect.

5.3 Replay never re-executes semantics

Replay uses stored events/artifacts/model-call records.

Replay must perform:

- zero initial model calls;
- zero repair calls;
- zero tools;
- zero retrieval;
- zero network;
- zero semantic generation.

Reproducibility means stored semantic outputs plus reducer/compiler versions reproduce the same canonical state.

5.4 Semantic model calls obey frozen budgets

No model call bypasses M02/Budget Meter.

Initial call and repair call each consume real call capacity.

Repair is not free.

A call must reserve budget before execution and settle/release according to the frozen Budget Meter semantics.

5.5 Exactly one repair attempt

Structured output may receive at most one repair attempt when the operation policy permits and budget remains.

There is no unbounded schema repair loop.

Repair is a real model call.

5.6 Repair and deterministic fallback are distinct

Repair:
- re-calls a semantic model;
- consumes budget;
- attempts the same semantic operation;
- remains model-assisted.

Fallback:
- is deterministic;
- does not pretend malformed output was valid;
- produces conservative state or a blocker;
- consumes no hidden model call.

The path used is auditable.

5.7 Source anchoring controls explicitness

An item may be EXPLICIT_INPUT only if a deterministic SourceAnchor resolves to source material that supports that interpretation.

No anchor:
→ cannot be EXPLICIT_INPUT.

Model-generated plausible statements are not explicit facts.

5.8 M01 uses irreversibility, not reversibility, in the allocation-facing vector

All M02-relevant difficulty axes must be harder-is-higher.

If semantic input uses reversibility:

irreversibility =
maximum_reversibility_score
- reversibility

or the deterministic ordinal-equivalent policy transform.

This makes monotonicity mechanically testable.

5.9 M01 weighted score is never sole tier authority

The policy order is:

semantic classification
→ deterministic risk floors
→ rule-based escalations
→ optional weighted/borderline score
→ frozen M02 allocation

A model response and weighted score cannot lower a mandatory floor.

5.10 Low confidence cannot make a task easier

Low confidence must conservatively preserve or increase effective difficulty according to versioned policy.

It must never silently reduce consequence, irreversibility, ambiguity, evidence scarcity, or search-space difficulty.

5.11 M03 uses explicit epistemic labels

Material extracted problem items use:

EXPLICIT_INPUT
SUPPORTED_INFERENCE
WORKING_ASSUMPTION
UNRESOLVED
CONTRADICTED

The label is part of the canonical semantics, not documentation.

5.12 M03 never demotes hard constraints

Constraint hardness and verification are distinct.

A constraint remains HARD even when:

- verifier is MODEL;
- verifier is HUMAN;
- verifier is UNAVAILABLE;
- current verification status is UNKNOWN;
- evaluation failed with ERROR.

HARD + UNKNOWN remains hard.

ERROR is not FAIL.

5.13 M03 surfaces contradictions rather than choosing a winner

Contradictory source claims must remain represented.

M03 uses frozen M09 contradiction semantics.

M03 does not resolve contradictions through model preference.

5.14 M03 prefers partial honest state over fabricated completeness

When semantic extraction fails or is unavailable, fallback preserves explicit state and marks unsupported semantics unresolved/blocked.

It does not fabricate a complete ProblemSpec.

5.15 M04 representations are projections

RepresentationPlan and RepresentationArtifact are versioned views over canonical state.

They never become a competing source of truth.

5.16 M04 compatibility scoring is deterministic

For a fixed:

ProblemSpec
TaskSignature
BudgetPlan
registry version
selection-policy version

the compatibility scores and deterministic selection must be identical.

5.17 Close scores preserve complementary lenses

A versioned tie-band policy governs secondary views.

If the two strongest compatible views are sufficiently close and the view budget permits two, retain both rather than forcing an arbitrary winner.

5.18 View budget remains authoritative

M04 cannot exceed:

BudgetPlan.search.max_representation_views

or the accepted equivalent.

5.19 Optional M04 adjudication is bounded

Model adjudication is optional and disabled by default.

When enabled, it may choose/explain among deterministic compatible candidates only.

It cannot:

- introduce an unregistered representation;
- override deterministic incompatibility;
- exceed the view budget;
- change ProblemSpec;
- change canonical facts.

5.20 Representation compilation is deterministic

Same canonical source state + builder version + configuration:
→ same canonical representation artifact hash.

Changed source state:
→ new/stale representation, never in-place mutation.

5.21 Frozen Waves 0–2 historic hashes remain compatible

Adding empty/default Wave 3 fields must not silently alter historic Wave 1/2 state hashes.

Use explicit conditional/versioned snapshot serialization.

5.22 Provider neutrality remains binding

Domain, M01, M03, M04, reducer, deterministic representation builders, and replay contain no provider-specific branching.

Wave 3 acceptance requires no real provider.

The deterministic fake adapter is sufficient.

8.1 Purpose

Provide one deterministic, versioned registry for model-assisted semantic operations.

Prompts are package resources or versioned registry definitions.

They are not anonymous module-local strings.

8.2 PromptDefinition

Each definition must include:

prompt_id
prompt_version
module_id
operation
model_role
input_contract_version
output_schema_id
output_schema_version
optional safety/profile identifier
template
template_hash

8.3 Initial prompt identities

Wave 3 initial prompt contracts:

m01.classify@1.0
m01.classify.repair@1.0

m03.formalise@1.0
m03.formalise.repair@1.0

m04.adjudicate@1.0
m04.adjudicate.repair@1.0

Do not create repair prompts for operations where repair is not permitted.

8.4 Template hash

Compute:

template_hash =
SHA-256(canonical prompt-definition preimage)

The preimage must exclude template_hash itself.

It must include every prompt field that materially changes semantic behavior.

8.5 Registration identity

Registry key:

(prompt_id, prompt_version)

Registering the exact same canonical definition twice may be idempotent.

Registering a materially different template under the same identity must fail:

PromptVersionConflict
or
PromptIntegrityError

8.6 Deterministic rendering

Rendering accepts only canonical operation inputs.

Rendering must not depend on:

- wall clock;
- random value;
- filesystem enumeration;
- map insertion order;
- unrelated conversation history;
- previous model prose not referenced canonically.

Set-like input values must use frozen canonical ordering.

8.7 Minimal context

Prompt input should contain the smallest relevant canonical state.

M01 receives task-classification inputs.

M03 receives formalisation inputs.

M04 optional adjudication receives the deterministic compatible representation candidate set.

Do not send the entire transcript by default.

8.8 Prompt acceptance tests

Prove:

- deterministic registry;
- deterministic template hash;
- duplicate identical registration idempotent;
- same identity/different template rejected;
- same identity/different schema identity rejected where semantically incompatible;
- render result deterministic;
- canonical unordered input ordering does not alter render;
- meaningful ordered input remains ordered;
- no clock/random dependence;
- prompt identity/version/hash persists into model-call record.

12. SEMANTIC MODEL RUNTIME
======================================================================

12.1 Purpose

Provide a narrow reusable runtime for model-assisted semantic calls.

It is not the full orchestrator.

12.2 Execution lifecycle

For each semantic call:

1. resolve prompt definition;
2. verify prompt integrity;
3. resolve output schema;
4. verify schema integrity;
5. deterministically render minimal prompt input;
6. compute canonical semantic input hash;
7. derive idempotency key;
8. look up persisted result for exact identity;
9. if reusable result exists, return persisted result;
10. otherwise reserve model-call/token budget;
11. call provider-neutral StructuredModelPort once;
12. store raw response as content-addressed artifact;
13. settle/release budget;
14. classify structured result;
15. persist operational model-call provenance;
16. return parsed proposal or typed failure to module validation.

12.3 Model-call identity

The call identity must include enough information to prevent prompt/schema drift reuse.

Conceptually:

run_id
+ module_id
+ operation
+ canonical_input_hash
+ module_version
+ policy_hash
+ prompt_id
+ prompt_version
+ template_hash
+ output_schema_id
+ output_schema_version

The exact canonical formula may adapt to accepted idempotency infrastructure.

12.4 Idempotent reuse

Repeated execution with identical identity returns the persisted result unless an explicitly versioned refresh policy is requested.

Do not re-call the model.

12.5 Raw response artifact

Raw response is stored separately from parsed proposal.

The artifact is content-addressed under existing artifact semantics.

A failed semantic result can leave a valid raw artifact record without producing canonical module state.

12.6 Model-call events

Use explicit event vocabulary such as:

ModelCallRecorded
ModelCallFailed

or an existing semantically equivalent call-record abstraction.

These records are provenance/operational state.

They do not assert epistemic truth.

12.7 Post-call event atomicity

Where model-call record + ArtifactRegistered are logically one persisted call record, commit them coherently.

If canonical module validation fails later, the call record may remain valid history while canonical M01/M03/M04 output is absent.

This is intentional.

12.8 Tests

Prove:

- deterministic call identity;
- idempotent result reuse;
- changed prompt version invalidates reuse;
- changed template hash invalidates reuse;
- changed schema version invalidates reuse;
- changed canonical input invalidates reuse;
- raw artifact persists;
- operational call record may exist without canonical module result;
- replay never invokes the port.

======================================================================
13. MODEL-CALL BUDGET INTEGRATION
======================================================================

13.1 No budget bypass

Every actual initial or repair model call must use the frozen Budget Meter.

13.2 Reservation

Before a call, reserve:

- one LLM call;
- maximum permitted input/output token capacity where configured;
- any additional deterministic resource vector required by accepted Budget Meter semantics.

13.3 Settlement

If adapter reports usage:

- record reported actual usage;
- settle according to reservation semantics;
- release unused reserved capacity.

13.4 Missing usage

If adapter does not report token usage:

- actual usage remains unknown;
- do not fabricate it;
- policy charge may conservatively equal reserved token capacity;
- distinguish policy charge from provider-reported actual usage.

13.5 Repair call

Repair requires a separate reservation and separate model call count.

No hidden free repair.

13.6 Budget unavailable

If budget cannot support the initial call:

- do not call;
- route directly to deterministic fallback/blocker.

If budget cannot support repair:

- do not overspend;
- route to fallback/blocker.

13.7 Tests

Prove:

- initial call reserves;
- settlement;
- unused capacity release;
- unknown reported usage remains unknown;
- conservative policy charge distinguishable;
- repair consumes a second call;
- repair refused when call budget unavailable;
- token reservation cannot oversubscribe;
- stale concurrent reservation still handled by frozen optimistic concurrency;
- semantic runtime cannot mutate BudgetRemaining outside events.
