# 5. Wave 2 architecture principles

Wave 2 remains **deterministic**.

The four modules must not require a real language model, retrieval provider, external research service, or human-input adapter to execute their core logic.

The architecture remains:

```text
authoritative event stream
        ↓
pure deterministic reducers
        ↓
versioned projections
        ↓
```

# 6. M09 — Epistemic Ledger

Implement the deterministic epistemic ledger as the authoritative provenance graph over claims, evidence, assumptions, unknowns, challenges, proposals, decisions, and revisions.

M09 is numbered ninth conceptually but is foundational and therefore belongs in Wave 2.

## 6.1 Ledger node model

Use the existing `LedgerNode` contract where possible.

Extend only if required by the authoritative architecture.

Node types must support at least:

```text
FACT
OBSERVATION
INFERENCE
ASSUMPTION
HYPOTHESIS
PROPOSAL
DECISION
UNKNOWN
CHALLENGE
EVIDENCE
ARTIFACT
```

If the current contract includes additional compatible types such as `CONTESTED`, preserve them according to the authoritative schema.

Each committed ledger node revision must retain:

- stable node identity;
- immutable revision number;
- node type;
- content;
- epistemic status;
- confidence assessment where applicable;
- source/artifact references;
- producing action/module provenance;
- schema version;
- creation timestamp.

Node revisions are immutable.

Changing a claim creates a new revision.

Never edit historical node content in place.

## 6.2 Epistemic statuses

Support the architecture-defined statuses:

```text
SUPPORTED
PROVISIONAL
CONTESTED
REFUTED
UNRESOLVED
STALE
```

Do not collapse epistemic status into a single boolean or confidence score.

A node can be high confidence yet stale.

A node can be provisional without being false.

## 6.3 Ledger relations

Support typed relations including:

```text
SUPPORTS
DEPENDS_ON
DERIVED_FROM
CONTRADICTS
SUPERSEDES
FALSIFIES
RESOLVES
OBSERVED_IN
EVALUATES
SELECTS
REJECTS
```

Use the existing `LedgerEdge` contract and extend only where necessary.

## 6.4 Graph invariants

The ledger is **not** one globally acyclic graph.

Enforce acyclicity only over the dependency/support relation family:

```text
SUPPORTS
DEPENDS_ON
DERIVED_FROM
```

for the relevant claim revision graph.

`CONTRADICTS` may be bidirectional.

`SUPERSEDES` must follow revision order.

No dangling node references are permitted.

A node must never depend on itself directly or transitively through dependency edges.

## 6.5 Revision semantics

Implement explicit node revision operations.

A revision must:

1. retain the stable logical node identity;
2. create a new immutable revision;
3. reference its predecessor;
4. preserve history;
5. mark affected downstream dependent nodes `STALE`.

Do not recursively rewrite descendant confidence values.

The architecture explicitly rejects naïve universal:

```text
child_confidence <= weakest_parent_confidence
```

propagation.

Confidence recomputation belongs to the relevant evaluator/module.

M09 only marks dependency consequences deterministically.

## 6.6 Confidence model

Preserve structured confidence.

Support the existing `ConfidenceAssessment` contract or equivalent architecture-defined structure:

```text
score
qualitative level
method
calibration group
evidence independence groups
explanation
```

M09 must not invent statistical calibration.

It stores and validates assessments.

Independent evidence may increase confidence.

When an upstream revision makes a descendant `STALE`, also derive an advisory,
non-authoritative `DependencyConfidenceEnvelope` describing which dependencies changed, structural
distance, known previous/current dependency-confidence ranges, confidence-delta interval when
defined, affected-dependency proportion, independence groups, method/version, and source event refs.
Unknown confidence stays unknown. The envelope may never mechanically replace/clamp the descendant's
authoritative `ConfidenceAssessment`.

## 6.6A Contradiction resolution and revision-chain integrity

A `CONTRADICTS` relation is open until explicitly resolved. `RESOLVES` must not be accepted as a
decorative edge: a production contradiction-resolution operation must atomically record the
contradiction(s), resolver/basis, explicit resolution outcome/status transitions (or successor
revisions), provenance, and affected `LedgerNodeRef` values. Preserve contradiction history while
the effective projection distinguishes OPEN from RESOLVED contradictions.

Hash-link each stable logical node's revision chain. Every revision stores `revision_hash`; revisions
after the first also store `predecessor_revision_hash`. Compute `revision_hash` from a canonical
preimage excluding itself but including predecessor hash plus immutable revision/provenance fields.
Reject mismatched chains. This supports incremental/local tamper verification while the full
`ledger_projection_hash` remains the whole-graph integrity check.

## 6.7 Ledger public operations

Do not expose direct mutation of the projection store.

All authoritative changes must emit events.

## 6.8 Ledger events

Use names appropriate to the existing event architecture, such as:


The exact vocabulary may differ if a more coherent minimal event set emerges, but:

- event meaning must be explicit;
- replay must reconstruct the exact ledger;
- provenance must be preserved;
- event schemas must remain versioned.

Do not use `GenericTestEvent` for real ledger behaviour.

## 6.9 Ledger projection

Implement a deterministic `LedgerProjection`.

It must allow efficient queries without becoming authoritative.

The projection must be rebuildable from events.

For a fixed event stream and projection version:

```text

```

must be stable.

# 7. M02 — Budget Allocator

Implement deterministic reasoning-tier allocation.

M02 consumes a `TaskSignature`.

M01 does not exist yet, so Wave 2 must test M02 against fixed synthetic `TaskSignature` fixtures.

Do not implement M01.

## 7.1 Tier model

Support:

```text
T0
T1
T2
T3
T4
T5
```

Load tier policy from versioned configuration rather than hard-coding module behaviour.

Preserve the manifest/architecture defaults.

The exact configured limits may include:

```text
max_iterations
max_llm_calls
max_tool_calls
max_input_tokens
max_output_tokens
max_candidates
max_concurrent_actions
max_runtime_seconds

initial_candidate_count

max_representation_views
synthesis_order_limit
falsifier_operator_limit
independent_validation_branches
sensitivity_samples

acquisition_threshold
stop_threshold
```

Fields that belong to later modules may still be allocated now as policy data without implementing their future behaviour.

## 7.2 Difficulty direction

Ensure all task-difficulty dimensions are monotonic in the harder direction.

The architecture uses `irreversibility`, not an inverted ambiguity-prone reversibility scale.

Relevant dimensions include:

```text
consequence
irreversibility
ambiguity
search-space complexity
evidence scarcity
```

and any additional already-defined signature dimensions.

## 7.3 Allocation algorithm

Use:

```text
mandatory tier floors
→ monotone policy rules
→ optional baseline score / thresholds
→ deployment ceilings
→ final explicit BudgetPlan
```

Do not allow one weighted scalar score to override hard tier floors.

High-consequence policy floors must dominate a low aggregate score.

The baseline weighted form may exist as configuration, but it is not authoritative over safety/consequence floors.

## 7.4 Monotonicity invariant

For two otherwise equivalent task signatures:

if any difficulty dimension increases and no dimension becomes easier, the allocated minimum tier must not decrease.

Property-test this.

## 7.5 Policy provenance and budget revisions

Every resolved tier policy is canonically hashed after defaults/overrides/floors/deployment inputs
are resolved. `BudgetAllocated` and `BudgetRevised` must persist `policy_version`, `policy_hash`, and
the realized `BudgetPlan` (plus optional policy artifact ref). Replay projects historic budget state
from committed events and must not silently recalculate it under a newer live policy.

Support deterministic revisions when later modules reveal additional complexity.

A revision may:

- raise a tier;
- redistribute **unused** optional capacity;
- reduce future optional work subject to policy.

A revision may never:

- reset consumed budget;
- erase expenditure;
- reduce mandatory validation below a consequence floor;
- make already-recorded usage disappear.

## 7.6 Budget events

Use typed events such as:

```text
BudgetAllocated  # binds policy_version + policy_hash
BudgetRevised    # binds policy_version + policy_hash
BudgetConsumed
BudgetReserved
BudgetReservationSettled
BudgetReservationReleased
```

Implement only reservations if genuinely required for the Wave 2 meter/concurrency model.

Do not prematurely build the full Wave 7 scheduler.

# 8. Budget Meter

Implement the executable deterministic `BudgetMeter`.

It is the sole authority for remaining resources.

No module may spend outside it.

## 8.1 Meter state

Track at minimum where represented by `BudgetPlan`:

```text
iterations
LLM calls
tool calls
input tokens
output tokens
candidate count where appropriate
runtime budget where deterministically measurable
```

Also preserve reservations if implemented.

## 8.2 Consumption semantics

Budget consumption must be represented by committed events.

The remaining budget must be a deterministic projection.

For every resource:

```text
remaining = allocated - committed usage - active reservations
```

where reservations exist.

Remaining values must never become silently negative.

Also derive a non-authoritative `BudgetBurnRate` projection from committed usage events only. For
each resource, where defined, expose trailing-window consumption per iteration/event, prior-window
rate, trend, ceiling proximity, and projected iterations to exhaustion. The window is event/iteration
count based, never replay-time wall clock. Zero/insufficient-data cases are explicit. Burn rate is a
control signal for M13, not a budget authority.

## 8.3 Reservation semantics

If concurrency-safe reservation support is introduced, it must:

- reserve before concurrent launch;
- reject oversubscription;
- settle actual usage;
- release unused reserved capacity;
- remain replay-deterministic.

Do not implement general action scheduling.

## 8.4 Hard ceilings

Hard ceilings are absolute.

A module request cannot bypass them.

Budget failure should produce typed outcomes/errors suitable for M13.

No “best effort” path may overspend and reconcile afterward.

## 8.5 Meter tests

Prove:

1. initial allocation;
2. zero usage;
3. deterministic consumption;
4. remaining calculation;
5. exact-ceiling consumption allowed where policy permits;
6. over-ceiling consumption rejected;
7. failed consumption does not mutate usage;
8. revision preserves consumed amount;
9. lower revised limits cannot invalidate already-consumed history;
10. concurrent reservations cannot oversubscribe;
11. release restores unused capacity;
12. replay reconstructs identical meter state;
13. meter hash/projection deterministic;
14. no direct mutable counter bypass exists.

# 9. M12 — Context Compiler

Implement deterministic context compilation from canonical projections.

M12 is not a generic summarizer.

It creates authoritative state packets suitable for:

- continuation;
- inspection;
- validation;
- transfer to another execution surface.

No model call is required.

## 9.1 Compiler inputs

Compile from versioned canonical/projection state such as:

```text
RunSnapshot
LedgerProjection
CandidateProjection
DecisionProjection
BudgetRemaining
CompilerProfile
size target
```

Wave 2 does not yet have full candidate or decision engines.

Therefore:

- support absent/empty future projections explicitly;
- compile the available deterministic state;
- do not fabricate candidates, decisions, or unknowns that do not exist yet.

Design the compiler interface so later projections can be added without changing packet semantics.

## 9.2 Profiles

Implement:

```text
FULL
STANDARD
HANDOFF
```

### FULL

Preserve all active decision-relevant canonical state and complete rejection/provenance information available at the current wave.

### STANDARD

Preserve:

- complete active state;
- decisive evidence;
- important assumptions;
- compact rejection register;
- unresolved high-value state where available.

### HANDOFF

Preserve the minimum sufficient authoritative state needed for safe continuation.

## 9.3 Required retained information

When present, packets must preserve:

- objective/output contract;
- hard constraints and verification status;
- fixed decisions and bases;
- verified facts;
- important assumptions;
- active and conditional frontier;
- rejected candidates with reasons;
- unresolved high-value questions;
- remaining budget;
- next action or terminal disposition.

Wave 2 may have many of these fields empty.

Empty must mean:

```text
not yet produced
```

not invented content.

## 9.4 Versioned compression rules

Compression order is a versioned compiler contract. Add a `ContextCompressionPolicy` containing
`compression_policy_version`, ordered rule IDs, profile eligibility, and mandatory-retention
classes. Default order:

1. canonical deduplication;
2. remove obsolete superseded revisions while retaining active revision + predecessor ref;
3. collapse redundant prose/excerpts already represented by canonical refs;
4. trim only profile-permitted low-leverage history;
5. stop before mandatory-retention data.

Record the compression-policy version/applied rules in compilation metadata so identical
input/profile/size/policy produces identical surviving content.

Never remove:

- rejection reasons;
- provenance needed to understand a decision;
- hard-constraint status;
- stale markers;
- unresolved blockers required for safe continuation.

## 9.5 Deterministic ordering

For fixed:

```text
snapshot_version
compiler_version
profile
size_target
```

compilation must produce identical canonical packet bytes/hash.

Define stable ordering for:

- node references;
- constraints;
- assumptions;
- rejected items;
- unresolved items;
- other set-like collections.

## 9.6 Context packet hash

Compute the packet hash over canonical packet content according to the repository's existing canonical serialization.

Avoid self-referential hashing.

If `packet_hash` is part of the serialized contract, define and document the exact preimage, e.g.:

```text
canonical packet representation excluding packet_hash
```

then set the calculated hash.

Test this explicitly.

## 9.7 Markdown rendering

Provide deterministic Markdown rendering from the canonical packet.

Markdown is a presentation projection.

It is not authoritative state.

For identical packet + renderer version:

```text
markdown bytes
```

must be stable.

Do not invoke an LLM renderer in Wave 2.

## 9.8 Overflow policy

A size target must not cause silent semantic truncation.

If required retained state cannot fit:

- first apply permitted deterministic compression;
- if still oversized, emit an explicit overflow diagnostic;
- do not silently drop required state.

## 9.9 Stale-state semantics

A stale node or decision must never appear as verified/current without being marked.

Profiles may omit stale historical items when permitted, but must not misrepresent them.

## 9.10 M12 events/artifacts

Context compilation itself does not mutate canonical reasoning state.

If packets are persisted:

- store canonical packet output as an artifact;
- event the compilation/reference where required;
- preserve compiler version, compression-policy version, and packet hash.

Do not make rendered Markdown an alternative canonical state source.

Support a deterministic `ContextDeltaPacket` as an optional derived transfer optimization. It binds
`base_packet_hash` and `target_packet_hash`, compiler/compression-policy/profile versions, ordered
ADD/REMOVE/REPLACE patch operations over canonical packet structure, and its own delta hash. Applying
a delta to the correct base must reproduce target canonical bytes/hash exactly; a wrong base hash
must fail. Persist/generate deltas only when policy says they materially reduce transfer size. A
delta is never canonical reasoning state and may never be the sole durable terminal context.

## 9.11 M12 tests

Prove:

1. FULL deterministic hash;
2. STANDARD deterministic hash;
3. HANDOFF deterministic hash;
4. recompilation idempotence;
5. stable ordering;
6. stable Markdown rendering;
7. packet hash preimage rule;
8. rejected reasons preserved;
9. stale claims not presented as verified;
10. empty future projections handled without fabrication;
11. required hard constraints preserved;

14. required information survives FULL → STANDARD → HANDOFF according to profile contract;

16. same input/profile/size/policy yields same surviving content;
17. overflow yields explicit diagnostic;

# 10. M13 — Marginal-Value Stop Controller

Implement deterministic run continuation/termination policy.

M13 chooses among:

```text
CONTINUE
COMPLETE
PARTIAL_BUDGET
BLOCKED
FAILED_INVARIANT
CANCELLED
```

It must never rely on unrestricted generative reasoning.

## 10.1 Inputs

Use architecture-compatible typed inputs such as:

```text
BudgetRemaining
ActionHistory
DecisionResult / decision state if present
RankedAcquisitionActions if present
AcceptanceStatus
ValidationStatus
CancellationState
```

Many later-wave inputs will not exist yet.

Wave 2 must support explicit absence rather than fabricate them.

## 10.2 Hard terminal precedence

Define deterministic precedence for hard terminal conditions.

At minimum handle:

### cancellation

Explicit user/system cancellation:

```text
CANCELLED
```

### invariant failure

Unrecoverable canonical-state or safety invariant violation:

```text
FAILED_INVARIANT
```

### hard budget exhaustion

If a hard ceiling prevents required continuation:

```text
PARTIAL_BUDGET
```

unless another higher-priority terminal condition applies.

### unresolved blocker

If required evidence/capability/permission is unavailable and no executable alternative exists:

```text
BLOCKED
```

### complete

Only when:

- required acceptance criteria are satisfied;
- mandatory validation is complete;
- no mandatory continuation condition remains.

Document and test the exact precedence where multiple terminal conditions are simultaneously true.

## 10.3 Mandatory continuation

Subject to hard ceilings, return `CONTINUE` when:

- mandatory tier action remains;
- decision-relevant hard constraint is unknown and a permitted resolution action exists;
- required independent validation remains incomplete;
- qualifying acquisition remains above threshold;
- frontier/recommendation remains materially unstable.

Later-wave signals may be absent in Wave 2 fixtures.

Use typed explicit states for “not applicable / not yet available”.

## 10.4 Soft completion

Implement configurable deterministic heuristics using already-available state:

```text
frontier stability
remaining decision-sensitive uncertainty
marginal expected value estimate
cost of next action
validation completeness
```

Do not claim mathematical convergence guarantees.

Soft stopping is heuristic.

Hard ceilings guarantee finite termination.

## 10.5 Confidence-bounded marginal-value semantics

Do not use one unqualified scalar point estimate as the soft-stop basis. Represent expected value
and normalized cost as bounded estimates with lower/point/upper values, method/version, confidence
assessment, and source/ledger refs. A point-only signal is a degenerate interval `[point, point]`.

Default conservative rule:

```text
value.lower >= cost.upper + threshold
    => definitely valuable; optional work may justify CONTINUE

value.upper < cost.lower + threshold
    => definitely not valuable; soft completion may be allowed if all other conditions hold

otherwise
    => overlapping/uncertain; default CONTINUE for decision-relevant work while hard budget remains,
       unless an explicit versioned policy selects another conservative treatment
```

Hard terminal and mandatory-continuation rules outrank this heuristic. `BudgetBurnRate` may inform
optional-work priority/proximity to exhaustion but cannot override a mandatory action or hard ceiling.

These are policy estimates, not objective truth. The policy version and basis must be persisted.

## 10.6 No forced “leader”

M13 must not assume a globally scalar-ranked leader.

It must operate with:

- a Pareto frontier;
- a provisional recommendation;
- no recommendation;
- or absent decision state.

Wave 2 tests should include “no decision result yet”.

## 10.7 Every decision has provenance

Every stop/continue result must record:

- disposition;
- reason codes;
- human-readable concise reasons;
- triggering references;
- concrete `ledger_trigger_refs` for every epistemic reason where a ledger node exists;
- policy version;
- relevant budget state/hash;
- burn-rate projection version/hash if consulted;
- marginal-value/cost estimate refs/confidence methods if consulted;
- context compilation request for terminal state.

For unresolved dependency/blocker, contested premise, or stale-evidence reasons, the corresponding
`LedgerNodeRef` is mandatory; generic refs may supplement but not replace it.

Do not store hidden chain-of-thought.

## 10.8 Terminal context packet invariant

Every terminal disposition must have a final context packet or a deterministic request/result that produces one.

The terminal flow should be:

```text
M13 terminal decision
        ↓
M12 deterministic final compilation
        ↓
persist/reference final ContextPacket
        ↓
terminal run state
```

Avoid dependency cycles in implementation.

M13 may request M12 compilation rather than requiring that the context packet already exist before deciding to terminate.

Define this lifecycle precisely.

## 10.9 Adversarial finite-termination guarantee

Add a test harness representing a module/action source that continually proposes optional work.

With finite hard limits, repeated stop-controller evaluation must eventually return:

```text
PARTIAL_BUDGET
```

or another appropriate terminal disposition.

This is the actual termination guarantee.

Do not rely on frontier convergence.

1. cancellation disposition;
2. invariant-failure disposition;
3. hard-budget partial disposition;
4. blocker disposition;
5. complete disposition;
6. continue disposition;
7. complete forbidden when a required criterion fails;
8. complete forbidden while mandatory validation remains;

20. bounded definitely-not-valuable case;

# 11. Resolve the M12 ↔ M13 dependency carefully

The conceptual architecture contains an apparent mutual relationship:

```text
M13 terminal decision → M12 final context
M12 context may contain terminal disposition / next action
```

Do not implement this as a cyclic Python dependency or recursive runtime call.

Use explicit contracts.

Recommended structure:

```text
M13
  produces StopDecision
  + optional ContextCompilationRequest

M12
  consumes snapshot + StopDecision/next-action state
  produces ContextPacket

runtime/service layer
  coordinates:
      StopDecision
      → compilation request
      → ContextPacket
      → final persisted terminal reference
```
