        ↓

        ↓
Budget Meter enforcing hard ceilings

5. BINDING WAVE 2 ARCHITECTURAL DECISIONS
======================================================================

5.1 Event log remains authoritative

Wave 2 state must derive from committed events.

Ledger projections, budget projections, compiled context metadata, stop projections, and metrics are rebuildable.

No module directly mutates canonical run state.

5.2 Pure deterministic core

M09, M02, Budget Meter, M12, and M13 are deterministic.

They must not require:

- model calls;
- tool calls;
- network access;
- retrieval;
- nondeterministic clocks;
- random UUIDs;
- filesystem enumeration order;
- unordered set iteration.

Persistent identifiers/timestamps must use existing injected deterministic clock/UUID facilities in tests.

5.3 Immutable epistemic history

Ledger nodes are immutable revisions.

Repairs or updates create successor revisions.

Status changes are evented.

Historical claims are never rewritten.

5.4 Ledger is a typed property graph, not one globally acyclic DAG

Only dependency/support relations participate in cycle rules.

Contradictions may be symmetric.

Supersession is temporal.

5.5 Confidence is structured

Do not universally enforce:

child_confidence <= weakest_parent_confidence

Independent evidence may increase confidence.

Upstream revision causes downstream staleness; it does not mechanically rewrite descendant confidence.

When dependency changes make a descendant STALE, M09 must additionally derive an advisory
DependencyConfidenceEnvelope. The envelope exists to tell downstream evaluators why trust may
have eroded and approximately how much of the dependency surface changed without turning that
signal into an authoritative confidence clamp. It is a deterministic projection, never a
replacement ConfidenceAssessment and never sufficient on its own to mark a claim REFUTED.

5.5A Contradiction resolution is explicit and atomic

CONTRADICTS may remain open indefinitely only while genuinely unresolved. A RESOLVES relation
must not be committed as a decorative edge that leaves both sides logically open. Resolving a
contradiction is an explicit operation that atomically records the resolution relation, the
resolver/basis, and the resulting epistemic status transitions (or explicit successor revisions).
Replay must therefore reconstruct both the historical contradiction and its resolved state.

5.5B Ledger revisions are hash-linked

Each logical node's immutable revision chain must be tamper-evident. Every revision records a
hash of its canonical revision preimage and, for revision > 1, the predecessor revision hash.
This is a Merkle-style hash link, not a claim that the entire property graph becomes one Merkle
tree. It enables incremental chain verification and localizes tampering while the existing
ledger_projection_hash remains the whole-projection integrity check.

5.6 Budget hard ceilings are authoritative

No action may consume beyond committed limits.

Oversubscription is rejected before event commitment.

Hard ceilings, not convergence assumptions, guarantee finite termination.

5.7 Tier allocation is monotone

A harder task signature cannot receive a lower minimum tier than an otherwise-equal easier signature.

Hard floors override weighted heuristics.

Every allocation/revision event must bind the resolved policy version and canonical policy hash
that produced it. Replay must project the committed plan from event data and must never silently
recompute an old allocation under whatever policy happens to be current at replay time.

Budget state also exposes an advisory deterministic burn-rate projection derived only from
committed usage events. Burn rate is not another spending authority; it is a control signal for
M13 showing consumption velocity and estimated proximity to hard ceilings.

5.8 Context is compiled state

M12 is not a prose summarizer.

Context packets are deterministic state projections.

Compression uses an explicit versioned priority policy so two compliant implementations cannot
choose different surviving content at the same size target. M12 may additionally emit
content-addressed delta packets between canonical context packets, but deltas are optimization
artifacts only: a delta must identify its base and target hashes and deterministically reconstruct
the complete target packet.

5.9 Stop logic is deterministic policy

M13 uses explicit state, resource, validation, blocker, stability, burn-rate, and marginal-value signals.

It does not assume a scalar global leader. Its soft marginal-value comparison is likewise not
restricted to one unqualified scalar point estimate: Wave 2 uses confidence-bounded/interval
estimates with a conservative policy for overlapping intervals. A point estimate is permitted
only as a degenerate interval.

Epistemic stop reasons must be tied directly to concrete LedgerNodeRef values where the relevant
claim/unknown/blocker is represented in M09. Generic triggering references may supplement these
refs but may not replace them for epistemic reasons.

5.10 M12/M13 coordination must not create a dependency cycle

M13 produces StopDecision and, for terminal outcomes, a ContextCompilationRequest.

M12 consumes state plus terminal/next-action information and produces the packet.

A minimal runtime/service layer coordinates the lifecycle.

5.11 Replay compatibility is mandatory

Existing Wave 1 event streams must continue to replay.

If the reducer version changes, compatibility must be explicit and tested.

10. M09 — EPISTEMIC LEDGER
======================================================================

10.1 Purpose

Provide the authoritative provenance and epistemic-state graph.

M09 is deterministic and shared.

10.2 Node model

Immutable node revisions represent at least:

- FACT
- OBSERVATION
- INFERENCE
- ASSUMPTION
- HYPOTHESIS
- PROPOSAL
- DECISION
- UNKNOWN
- CHALLENGE
- EVIDENCE
- ARTIFACT

Preserve compatible existing types such as CONTESTED if already present.

Each node revision must retain:

- stable logical node ID;
- positive revision;
- node type;
- content;
- effective epistemic status;
- confidence assessment where applicable;
- source/artifact references;
- schema version;
- created_at;
- created_by_action;
- producing module;
- provenance.

10.3 Epistemic statuses

Support:

- SUPPORTED
- PROVISIONAL
- CONTESTED
- REFUTED
- UNRESOLVED
- STALE

Do not collapse epistemic status into truth/falsity.

10.4 Relations

Support:

- SUPPORTS
- DEPENDS_ON
- DERIVED_FROM
- CONTRADICTS
- SUPERSEDES
- FALSIFIES
- RESOLVES
- OBSERVED_IN
- EVALUATES
- SELECTS
- REJECTS

10.5 Dependency normalization

For traversal and cycle detection normalize all dependency relations to prerequisite → dependent.

Recommended normalization:

SUPPORTS:
stored source → target

DEPENDS_ON:
stored target → source for dependency traversal

DERIVED_FROM:
stored target → source for dependency traversal

The implementation must document this rule so ancestor/descendant semantics are unambiguous.

10.6 Acyclicity

Only normalized:

- SUPPORTS
- DEPENDS_ON
- DERIVED_FROM

participate in cycle detection.

CONTRADICTS may be bidirectional.

SUPERSEDES is validated independently as temporal revision lineage.

10.7 Edge validation

Reject:

- dangling node references;
- direct self-dependency;
- indirect dependency cycle;
- invalid revision references;
- invalid supersession;
- supersession across different stable logical IDs where the model requires same-ID revisions.

10.8 Supersession

Recommended semantics:

new revision → immediate predecessor

Require:

new_revision == predecessor_revision + 1

Preserve all historical revisions.

10.9 Status transitions

Do not rewrite immutable node content to change effective status.

Use explicit status-transition events or equivalent immutable overlays.

10.10 Revision lifecycle

A revision operation should:

1. validate predecessor;
2. create successor revision;
3. add SUPERSEDES relation;
4. compute dependent descendants from the pre-revision graph;
5. emit deterministic sorted staleness event(s);
6. mark effective dependent status STALE without rewriting historical content/confidence.

10.11 Confidence

Preserve structured confidence fields such as:

- score;
- qualitative level;
- method;
- calibration group;
- evidence independence groups;
- explanation.

M09 validates and stores confidence.

It does not perform universal confidence propagation.

10.11A Advisory dependency confidence envelope

When a committed upstream revision causes descendants to become STALE, derive a
DependencyConfidenceEnvelope for each affected descendant. This is non-authoritative metadata
for later evaluators, not a replacement confidence assessment and not a pruning/stop decision.

The envelope should contain, where available:

- affected_node_ref;
- changed_dependency_refs;
- dependency_distance / maximum affected dependency depth;
- previous dependency confidence range;
- current dependency confidence range;
- confidence_delta interval when both sides are known;
- number/fraction of direct dependencies changed;
- independence-group information relevant to the affected dependencies;
- method/version;
- explanation / reason code;
- source event refs.

Rules:

- UNKNOWN confidence remains unknown; never invent a numeric score.
- The envelope may indicate NO_NUMERIC_ESTIMATE when only structural impact is known.
- No consumer may interpret the envelope as child_confidence = envelope.minimum.
- The envelope is rebuildable from committed ledger state/events.
- Re-evaluation may replace the descendant's ConfidenceAssessment only through a new authoritative
  evaluator event, never by the envelope itself.

10.11B Formal contradiction resolution

CONTRADICTS edges represent an open contradiction until an explicit resolution operation is
committed.

Implement resolve_contradiction (or equivalent) as one atomic command/batch that records:

- the contradiction edge(s) being resolved;
- a RESOLVES relation tied to a concrete resolver node/evidence/basis;
- an explicit resolution outcome or explicit status-transition set;
- the affected LedgerNodeRef values;
- provenance and action/module refs.

The reducer/runtime must reject a production RESOLVES relation that is committed without the
corresponding resolution record/status transitions in the same valid batch. Do not infer that one
side is true merely from the existence of RESOLVES; the outcome is explicit.

Resolution must preserve historical CONTRADICTS edges while the effective projection marks the
contradiction CLOSED/RESOLVED (or equivalent). queries for contradictions must be able to
distinguish open from resolved contradictions.

10.12 Queries

Implement deterministic queries:

- append_node
- append_edge
- revise_node
- mark_status
- ancestors
- descendants
- contradictions (with open/resolved filtering)
- unresolved_dependencies
- dependency_confidence_envelopes
- verify_revision_chain
- query_by_type
- materialise_projection
- validate_graph

Definitions:

ancestors = upstream dependency/support prerequisites

descendants = downstream dependents

unresolved_dependencies = dependency-family ancestors whose effective state is not SUPPORTED

All set-like query results must use stable deterministic ordering.

10.13 Projection hash and revision-chain integrity

LedgerProjection must have a stable canonical hash.

The same event stream + projection version must produce the same projection bytes/hash.

Each immutable LedgerNode revision must additionally carry:

- revision_hash;
- predecessor_revision_hash (null only for the first revision).

Define revision_hash as SHA-256 over a canonical revision preimage that excludes revision_hash
itself but includes predecessor_revision_hash and the immutable revision payload/provenance fields.
A successor must match the stored predecessor hash before it can commit.

This forms a hash-linked revision chain per stable logical node. It enables incremental verification
of newly appended revisions and local tamper detection without claiming that verification of the
entire multi-node ledger graph is O(1). The whole-projection hash remains the cross-node integrity
check.

Expose verify_revision_chain(node_id, from_revision=...) or an equivalent deterministic validator.

10.14 Ledger errors

- DanglingLedgerReference

12. EXECUTABLE BUDGET METER
======================================================================

12.1 Purpose

Budget Meter is the sole authority for remaining resources.

No future module may spend outside it.

12.2 Tracked resources

Track, where allocated:

- iterations;
- LLM calls;
- tool calls;
- input tokens;
- output tokens;
- candidate count where meaningful;
- runtime seconds;
- active concurrent reservations.

12.3 Deterministic formula

For every resource:

remaining =
allocated
- committed usage
- active reservations

No replay-time wall clock is permitted.

Runtime usage is committed explicitly.

12.4 Consumption

Direct usage creates BudgetConsumed event(s).

Exact-ceiling consumption is permitted.

Over-ceiling consumption is rejected before persistence.

Rejected consumption changes nothing.

12.5 Reservations

Implement minimal reservations because Wave 2 must prove oversubscription prevention.

A reservation:

- belongs to an action ID;
- reserves a complete resource vector;
- counts against max_concurrent_actions;
- is evented;
- is replayable.

12.6 Settlement

Settlement:

- removes the reservation;
- records actual committed usage;
- must not exceed reservation;
- releases unused reserved capacity.

12.7 Release

Failed/cancelled work releases reservation.

Release restores unused capacity.

12.8 Concurrency

Competing reservations from the same snapshot are resolved by optimistic event append.

Only one stale-snapshot writer may succeed.

The loser reloads.

If capacity is exhausted after reload, reservation fails.

12.9 Revision interaction

Budget revision must account for:

committed usage + active reservations

A revision that falls below this total is invalid.

12.9A Advisory burn-rate projection

Derive BudgetBurnRate only from committed budget events. It is advisory control-state for M13,
not spending authority.

For each tracked resource, expose where mathematically defined:

- committed amount;
- remaining amount;
- consumption_per_iteration over a configured deterministic trailing window;
- consumption_per_usage_event over that window;
- previous-window consumption rate;
- trend = INCREASING | STABLE | DECREASING | INSUFFICIENT_DATA;
- projected_iterations_to_exhaustion when rate > 0;
- ceiling_proximity ratio;
- window definition/version;
- source event range/hash.

The trailing window is defined by committed iteration/event count, never replay-time wall clock.
If a denominator is zero or data is insufficient, return an explicit unavailable state rather than
infinity or an invented estimate.

Burn-rate projection must be replay-deterministic and must never modify BudgetRemaining. M13 may
use it to reason about whether continuing optional work is likely to collide with a hard ceiling.

13.8 Versioned compression order

Compression order is part of the compiler contract, not an implementation detail.

Define a ContextCompressionPolicy with:

- compression_policy_version;
- ordered rule IDs;
- per-profile rule eligibility;
- mandatory-retention classes;
- size metric = canonical UTF-8 bytes.

The default Wave 2 rule order is fixed and versioned:

C01 — canonical deduplication of identical entries;
C02 — remove obsolete superseded revisions while retaining active revision + predecessor link;
C03 — collapse duplicate/redundant prose or excerpts already represented by canonical refs;
C04 — trim profile-permitted low-leverage historical detail;
C05 — stop compression; never cross a mandatory-retention boundary.

version must choose the same surviving canonical content.

- stale status;
- unresolved blocker;
- rejection reason;
- decision provenance;
- remaining budget;
- next action;
- terminal disposition.

14. M13 — MARGINAL-VALUE STOP CONTROLLER
======================================================================

14.1 Purpose

Return a deterministic continuation/termination decision.

Supported dispositions:

- CONTINUE
- COMPLETE
- PARTIAL_BUDGET
- BLOCKED
- FAILED_INVARIANT
- CANCELLED

14.2 Inputs

Use typed inputs:

- BudgetRemaining;
- ActionHistory;

- optional ranked acquisition availability;
- AcceptanceStatus;
- ValidationStatus;
- CancellationState;
- BlockerState;
- StopPolicy;
- BudgetBurnRate if available;
- frontier stability signals if available;
- bounded marginal next-action value/cost signals if available.

Later-wave inputs may not exist yet.

Use explicit NOT_PRODUCED / NOT_APPLICABLE states.

14.3 Hard terminal precedence

Use deterministic precedence.

Recommended order:

1. explicit cancellation → CANCELLED;
2. unrecoverable invariant failure → FAILED_INVARIANT;
3. hard ceiling prevents required continuation → PARTIAL_BUDGET;
4. required unresolvable blocker with no executable alternative → BLOCKED;
5. mandatory continuation condition → CONTINUE;
6. acceptance satisfied + validation complete + stable/no qualifying work → COMPLETE;
7. executable work remains → CONTINUE;
8. no executable work + unresolved required state → BLOCKED.

Document exact precedence.

14.4 Cancellation

Explicit cancellation yields CANCELLED.

14.5 Invariant failure

Unrecoverable canonical-state or safety invariant yields FAILED_INVARIANT.

14.6 Budget exhaustion

If additional required work is needed but a hard ceiling prevents it:

PARTIAL_BUDGET

Do not return PARTIAL_BUDGET if the run is already legitimately complete.

14.7 Blocker

If required evidence/capability/permission is unavailable and no permitted alternative exists:

BLOCKED

14.8 Mandatory continuation

Subject to hard ceilings, CONTINUE when:

- mandatory tier action remains;
- resolvable required unknown remains;
- mandatory validation remains;
- qualifying acquisition remains;
- frontier/recommendation is unstable where such state exists.

14.9 Completion

COMPLETE only when:

- required acceptance criteria satisfied;
- no known required criterion fails;
- mandatory validation complete;
- no mandatory continuation remains;
- state stable enough under active policy;
- no qualifying next action remains.

14.10 Confidence-bounded marginal-value policy

Do not reduce the soft-stop decision to one unqualified scalar point estimate.

Represent expected value and normalized cost as bounded estimates:

MarginalValueEstimate:
- lower;
- point (optional);
- upper;
- ConfidenceAssessment;
- method/version;
- source/ledger refs.

CostEstimateInterval:
- lower;
- point (optional);
- upper;
- method/version;
- source refs.

A point-only signal is represented as the degenerate interval [point, point].

Default conservative comparison:

DEFINITELY_VALUABLE:
    value.lower >= cost.upper + stop_threshold
    → optional work may justify CONTINUE

DEFINITELY_NOT_VALUABLE:
    value.upper < cost.lower + stop_threshold
    → soft completion may be allowed if all other completion conditions hold

OVERLAP / UNCERTAIN:
    intervals overlap or confidence is insufficient
    → default CONTINUE when work is decision-relevant and hard budget remains,
      unless an explicit versioned policy selects another conservative treatment

Hard terminal/mandatory-continuation rules always outrank this soft heuristic.

BudgetBurnRate may modify the advisory priority of continuing optional work (for example by showing
that the projected exhaustion horizon is shorter than the expected work horizon), but it cannot
override a mandatory action or hard ceiling.

These remain heuristic policy estimates. Do not present them as calibrated truth unless they are
later produced by a calibrated model.

14.11 No scalar leader

- there is a Pareto frontier;
- there is a provisional recommendation;
- there is no recommendation;
- DecisionResult is not yet produced.

For reason codes such as unresolved dependency, unresolved blocker, contested premise, or stale
evidence, the corresponding ledger_trigger_refs are mandatory. A generic object/action reference
may supplement but not replace the concrete ledger reference.

No hidden chain-of-thought.
